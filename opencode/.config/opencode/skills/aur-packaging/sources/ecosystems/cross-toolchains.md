## <span id=".E7.89.88.E6.9C.AC.E5.85.BC.E5.AE.B9.E6.80.A7"></span>版本兼容性

</div>

<div class="archwiki-template-box archwiki-template-box-warning">

**警告：**使用不兼容版本的软件包编译工具链必然会失败。一般来说，不同版本之间都不兼容。

</div>

建议按照以下策略选择 gcc、binutils、内核和 C 库的兼容版本：

- 总则：
  - gcc 和 binutils 的版本相关，建议使用同时发布的版本；
  - 建议使用最新的内核头文件来编译 libc，但使用 `--enable-kernel`（只保证适用于 glibc，其他 C 库可能约定不同）能强制在旧内核上工作；
- [官方仓库](../zh-cn/%E5%AE%98%E6%96%B9%E4%BB%93%E5%BA%93.html "官方仓库")：可能需要额外的修正，但 Arch Linux（或其特定架构的分支）使用的版本很可能可以协同工作；
- 软件文档：所有 GNU 软件都有 `README` 和 `NEWS` 文件，涵盖了依赖关系的最低版本要求等内容；
- 其他发行版：同样也进行交叉编译
- <a href="https://trac.clfs.org" class="external free" rel="nofollow">https://trac.clfs.org</a> 涵盖了构建交叉编译器的必要步骤以及一些依赖的最新版本。

<div class="mw-heading mw-heading2">

## <span id=".E6.9E.84.E5.BB.BA.E4.BA.A4.E5.8F.89.E7.BC.96.E8.AF.91.E5.99.A8"></span>构建交叉编译器

</div>

构建交叉编译器的一般方法是：

1.  binutils：构建为目标架构链接、处理的 cross-binutils。
2.  头文件：安装目标架构的 C 库和内核头文件。
    1.  参考 <span class="nobreak"><span class="plainlinks archwiki-template-pkg"><a href="https://archlinux.org/packages/?name=linux-api-headers" class="external text" rel="nofollow">linux-api-headers</a></span><sup><span class="small">包</span></sup></span>，并将 `ARCH=`*`target-architecture`* 参数传给 *make*
    2.  打包 libc 头文件 (<a href="https://sourceware.org/legacy-ml/crossgcc/2003-06/msg00170.html" class="external text" rel="nofollow">此处</a>描述了 Glibc 的处理方法)
3.  gcc 第 1 阶段：构建基本的（第 1 阶段）gcc 交叉编译器。这将被用来编译 C 库，但是几乎不能编译其他任何东西（因为无法链接不存在的 C 库）。
4.  libc：构建交叉编译的 C 库（使用第 1 阶段的交叉编译器）。
5.  gcc 第 2 阶段：构建完整的（第 2 阶段）C 交叉编译器。

头文件和 libc 的源代码因平台而异。

<div class="archwiki-template-box archwiki-template-box-tip">

**提示：**根据需求的不同，具体操作步骤也不尽相同。例如，如果想创建内核和 glibc 版本与 Arch Linux 系统相同的 "克隆版"，可不构建头文件直接将 `--with-build-sysroot=/` 传给 `configure`。

</div>

<div class="mw-heading mw-heading2">

## <span id=".E8.BD.AF.E4.BB.B6.E5.8C.85.E5.91.BD.E5.90.8D"></span>软件包命名

</div>

软件包名称*不*应以 `cross-` 开头（之前建议使用前缀 `cross-`，但可能由于包名太长，在正式的软件包中未被采用），而应由软件包名称组成，前缀为 <a href="https://wiki.debian.org/Multiarch/Tuples" class="extiw" title="debian:Multiarch/Tuples">GNU triplet</a>，不含厂商字段或在厂商字段中含 "unknown"。例如：`arm-linux-gnueabihf-gcc`。如果存在更短的命名规则（例如：`mips-gcc`），可以使用但并不建议。

<div class="mw-heading mw-heading2">

## <span id=".E6.94.BE.E7.BD.AE.E6.96.87.E4.BB.B6"></span>放置文件

</div>

最新版本的 gcc 和 binutils 对系统根目录和库使用不冲突的路径。可执行文件应放在 `/usr/bin/` 中。为防止冲突，应在所有文件前加上架构名称。

通常来说，`./configure` 应至少含以下参数：

\_target=*your_target*\
\_sysroot=/usr/lib/\${\_target}\
...\
./configure \\\
    --prefix=\${\_sysroot} \\\
    --sysroot=\${\_sysroot} \\\
    --bindir=/usr/bin

其中 *`your_target`* 可自行修改，例如修改为 "i686-pc-mingw32"。

<div class="mw-heading mw-heading2">

## <span id=".E7.A4.BA.E4.BE.8B"></span>示例

</div>

此处以 MinGW 的 binutils 的 PKGBUILD 为例。需要注意的是：

- 指定交叉编译环境的根目录
- 使用 `${_pkgname} `、`${_target} ` 和 `${_sysroot} ` 能使代码更易读
- 删除重复或冲突的文件

\# Maintainer: Allan McRae \<allan@archlinux.org\>\
\
\# cross toolchain build order: binutils, headers, gcc (pass 1), w32api, mingwrt, gcc (pass 2)\
\
\_target=i686-pc-mingw32\
\_sysroot=/usr/lib/\${\_target}\
\
pkgname=\${\_target}-binutils\
\_pkgname=binutils\
pkgver=2.19.1\
pkgrel=1\
pkgdesc="MinGW Windows binutils"\
arch=('i686' 'x86_64')\
url="http://www.gnu.org/software/binutils/"\
license=('GPL')\
depends=('glibc\>=2.10.1' 'zlib')\
options=('!libtool' '!distcc' '!ccache')\
source=(http://ftp.gnu.org/gnu/\${\_pkgname}/\${\_pkgname}-\${pkgver}.tar.bz2)\
md5sums=('09a8c5821a2dfdbb20665bc0bd680791')\
\
build() {\
  cd \${srcdir}/\${\_pkgname}-\${pkgver}\
  mkdir binutils-build && cd binutils-build\
\
  ../configure --prefix=\${\_sysroot} --bindir=/usr/bin \\\
    --with-sysroot=\${\_sysroot} \\\
    --build=\$CHOST --host=\$CHOST --target=\${\_target} \\\
    --with-gcc --with-gnu-as --with-gnu-ld \\\
    --enable-shared --without-included-gettext \\\
    --disable-nls --disable-debug --disable-win32-registry\
  make\
  make DESTDIR=\${pkgdir}/ install\
  \
  # clean-up cross compiler root\
  rm -r \${pkgdir}/\${\_sysroot}/{info,man}\
}\

<div class="archwiki-template-box archwiki-template-box-note">

**注意：**在交叉编译工具链构建过程中，每次都从独立的目录中执行 `configure` 和 *make* 命令（所谓的树外编译），并在 [PKGBUILD](../zh-cn/PKGBUILD.html "PKGBUILD") 发生变化后删除整个 `src` 目录（即使变化很小）。

</div>

## <span id=".E7.96.91.E9.9A.BE.E8.A7.A3.E7.AD.94"></span>疑难解答

</div>

<div class="mw-heading mw-heading3">

### <span id=".E4.B8.BA.E4.BB.80.E4.B9.88.E4.B8.8D.E5.AE.89.E8.A3.85.E5.88.B0_.2Fopt.EF.BC.9F"></span>为什么不安装到 /opt？

</div>

有以下两个原因：

1.  首先，根据文件系统层次结构标准 (FHS)，这些文件只位于 `/usr` 的某个位置。
2.  其次，安装到 `/opt` 是退而求其次的选择。

<div class="mw-heading mw-heading3">

### <span id=".22.E8.B7.AF.E5.BE.84.E5.A4.96.E7.9A.84.E5.8F.AF.E6.89.A7.E8.A1.8C.E6.96.87.E4.BB.B6_.28out-of-path_executables.29.22_.E6.98.AF.E4.BB.80.E4.B9.88.EF.BC.9F"></span>"路径外的可执行文件 (out-of-path executables)" 是什么？

</div>

这看起来很奇怪，但能让交叉编译更容易。有时项目的 Makefile 不使用 `CC` 或其他变量，而是直接使用 **gcc** 。在尝试交叉编译这样的项目时，编辑 Makefile 可能会很麻烦。然而，将 `$PATH` 改为优先使用我们的可执行文件即可解决此问题，只需将 `make` 改为执行 `PATH=/usr/`*`arch`*`/bin/:$PATH make`。

## <span id=".E6.95.85.E9.9A.9C.E6.8E.92.E9.99.A4"></span>故障排除

</div>

<div class="mw-heading mw-heading3">

### <span id=".E7.BC.96.E8.AF.91.E5.A4.B1.E8.B4.A5.E4.BD.86.E6.B2.A1.E6.9C.89.E6.98.8E.E7.A1.AE.E7.9A.84.E6.8F.90.E7.A4.BA.E5.BA.94.E8.AF.A5.E5.A6.82.E4.BD.95.E8.A7.A3.E5.86.B3.EF.BC.9F"></span>编译失败但没有明确的提示应该如何解决？

</div>

如果是在运行 `configure` 时发生的错误，参见 `$srcdir/`*`pkgname`*` -build/config.log`。如果是在编译过程中发生的错误，请向上滚动控制台日志或搜索 "error" 一词。

<div class="mw-heading mw-heading3">

### <span id=".5Berror_message.5D_.E9.94.99.E8.AF.AF.E6.84.8F.E5.91.B3.E7.9D.80.E4.BB.80.E4.B9.88.EF.BC.9F"></span>\[error message\] 错误意味着什么？

</div>

很可能犯了一些不明显的错误：

- 配置标志位过多或过少。尝试使用已证明有效的标志位。
- 依赖关系被破坏。例如，binutils 文件放错位置或丢失，可能导致 gcc 配置过程中出现晦涩难懂的错误信息。
- 未在 `build()` 函数中添加 `export CFLAGS=""`（参见 GCC Bugzilla 中的 <a href="https://gcc.gnu.org/bugzilla/show_bug.cgi?id=25672" class="external text" rel="nofollow">bug 25672</a>）。
- 某些 `--prefix` 或 `--with-sysroot` 参数组合可能要求目录可写。
- 系统根目录缺少内核头文件或 libc 头文件。
- 如果通过搜索引擎仍无法解决，建议立刻放弃当前配置，尝试更稳定、更成熟的配置。

<div class="mw-heading mw-heading3">

### <span id=".E4.B8.BA.E4.BB.80.E4.B9.88.E6.96.87.E4.BB.B6.E5.AE.89.E8.A3.85.E4.BD.8D.E7.BD.AE.E4.BC.9A.E4.B8.8D.E6.AD.A3.E7.A1.AE.EF.BC.9F"></span>为什么文件安装位置会不正确？

</div>

执行 `make install` 命令的各种方法会产生不同的结果。例如，有些 make 目标可能不提供 `DESTDIR` 支持，而是要求使用`install_root`。对于 `tooldir`、`prefix` 和其他类似参数也是如此。有时提供参数而不是环境变量，例如

./configure CC=arm-elf-gcc\

而不是

CC=arm-elf-gcc ./configure\

反之亦然，可能会导致不同的结果（通常是因为 configure/make 递归地调用自身）。
